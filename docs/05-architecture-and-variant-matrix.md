# Architecture decision + the Variant Matrix (the generative engine)

**Date:** 2026‑06‑14
**Status:** Decision recorded (Phase 3 "Function" direction)

Answers two questions raised by the stakeholder:
1. Synthesize all the text‑effect / animation / intro‑outro / transition concepts into **one combinatorial
   matrix** that we combine **by logic or fully at random** → endless fresh title ideas.
2. **Monolith vs. building the OGraf `.zip`? Firebase?** → **Monolith. No Firebase.** (Details below — the
   two aren't actually rivals.)

---

## 1. The Variant Matrix (core idea)

Instead of a fixed list of "looks", the product is a set of **orthogonal axes**. A *look* = one point in
that space; **random** = sample each axis; **logic** = curated rules/weights that keep combos tasteful. The
9 named looks we have are just **9 anchor points** in a space of millions.

| # | Axis (category) | Example options |
|---|---|---|
| 1 | **Entrance (intro)** | fade · rise · mask‑wipe · typewriter · scale‑pop · blur‑in · scatter‑in · line‑mask |
| 2 | **Exit (outro)** | fade · sink · wipe‑out · dissolve · shatter · scale‑down (often mirror of entrance) |
| 3 | **Idle / emphasis** (while held) | none · pulse · float · wobble · flicker · shimmer · weight‑breathe (variable font) |
| 4 | **Unit & order** | char / word / line × order: L→R · R→L · center‑out · random |
| 5 | **Material (skin)** | neon · chrome · glitch · gradient · brutalist · retro · glass · fire · particles · mono |
| 6 | **Typography** | family · weight · tracking · case |
| 7 | **Palette** | mono · single accent · duo‑gradient (+ named moods: energetic/dreamy/aggressive/elegant) |
| 8 | **Motion feel** | easing curve · speed · stagger amount |
| 9 | **Background** | transparent (default, for Resolve) · grain · glow |

**Combination logic**
- **Random:** sample each axis — but through a **taste layer** of *constraints & weights* so results stay
  good (e.g. `material:glitch` → favors RGB‑split idle + hard easing; `type:serif` → elegant easings;
  background stays transparent by default for Resolve).
- **Rule/logic presets:** curated regions of the space; the named looks (Neon, Chrome…) are saved coordinates.
- **Seed:** every generated variant = a small **seed / short code**. Same seed → same variant. This gives
  *both* "endless fresh ideas" (new seed) **and** reproducibility + shareability (keep/share the code).
  **The seed _is_ the data — no database required.**

> Mental model: `variant = combine(matrix, seed)` → renders the same way every time. "Surprise me" = new
> seed; "I like this one" = keep the seed.

---

## 2. Decision: **Monolith. No Firebase.**

**The tool is a self‑contained monolith** (one web app, all logic + matrix baked in, no backend):
- **Mission fit:** "free for everyone" → no server costs, no sign‑up, works **offline**, private by default.
- **The matrix is tiny:** structured JSON (the axes + options + weights) + a pure `combine()` function. That
  belongs **in the app**, not in a database.
- **Simplicity:** nothing to host, deploy, or rate‑limit; one file/app ships everywhere.

**Firebase / a cloud DB is NOT needed for the engine.** It would only earn its place **later, optionally**, as
a *community layer* — e.g. sharing user‑saved seeds, a public gallery, "trending combos." Even then, because a
variant is just a **seed**, sharing is a string, not a DB dependency. **Not now.**

---

## 3. Monolith vs. the OGraf `.zip` — not rivals

These are **different things**, so we don't have to choose:
- **Monolith** = *how the tool is built* (the app + matrix + engine, self‑contained).
- **`.ograf.zip`** = *what the tool exports* for Resolve. OGraf **requires** a package: a manifest
  `*.ograf.json` (the entrypoint) + a `main` `.mjs` (the Web Component) + resources.

**We make the output as monolithic as the spec allows** — and this also **de‑risks Resolve** (Dossier #1: its
external‑asset loading is undocumented, so self‑contained is safest):

```
my-line.ograf.zip
├── my-line.ograf.json     ← tiny manifest (entrypoint; required as a separate file)
└── graphic.mjs            ← ONE module: the look + the matrix-rendered animation +
                             goToTime(), CSS inlined, FONTS inlined as base64
```

So the minimum is **two files** (the spec forces the manifest to be separate), but everything else —
animation, styles, fonts — is **inlined into the single `.mjs`**. That is "monolith in spirit," fully
self‑contained, and it's the **real testable package** for Resolve.

**Preferred answer: Monolith** — and the `.ograf.zip` comes almost for free as a thin required wrapper
(manifest + one inlined `.mjs`), generated by the monolith at export time. No Firebase.

---

## 4. How this maps to the plan

- **Phase 3 (Function):** build the **matrix + `combine(seed)`** engine inside the existing monolith, so
  "Generate" produces genuinely fresh random/logic‑driven variants (not the fixed 9). Stays 100% in‑browser —
  no Resolve, no backend.
- **Phase 4 (Technique):** the export wraps a chosen variant into the self‑contained `.ograf.zip`
  (manifest + inlined `.mjs` with `goToTime()`), then test in Resolve 21.

*Decision owner: stakeholder. Recorded here so we build the engine as a baked‑in monolith with a seed‑based
variant matrix, exporting self‑contained OGraf packages — no database.*
